## 一、任务总则与全局约定

### 1.1 总则

1. 实现一个前后端分离的通用后台管理系统，功能域仅四个：登录、用户管理、角色管理、菜单管理。
2. 本文件是唯一需求来源。写明的必须照做；没写的按最小实现原则处理，**不要自行增加功能**（不要加部门、字典、定时任务、通知、工作流、代码生成器、图表）。
3. **不要更换技术栈**，不要引入本文件未列出的框架。
4. 所有命名（包名、类名、接口地址、字段名、权限标识字符串）必须与本文件逐字一致。前后端、数据库种子数据靠这些字符串对齐，改动任意一个都会导致权限失效。
5. 最终必须做到：后端能编译启动、前端能构建启动、能登录、页面能跑通、权限校验能生效。

### 2.2 Maven 继承与依赖方向（严格单向，禁止循环）

- `admin-dependence` 的父 POM 是 `spring-boot-starter-parent`，自身打包为 pom，集中放版本属性与 dependencyManagement。
- 其余所有模块的父 POM 指向 `admin-dependence`。**父 POM 必须同时写 artifactId 与 relativePath**，relativePath 从该模块目录出发，写清到达 admin-dependence 的相对路径，不要依赖默认值 `../pom.xml`：
  - `admin-backend/pom.xml` → `<relativePath>./admin-dependence/pom.xml</relativePath>`
  - `admin-backend/admin-common/pom.xml`（其余同级业务模块同理）→ `<relativePath>../admin-dependence/pom.xml</relativePath>`
  - 这一点是本项目最容易一次写错的配置，写完请逐个模块确认能解析到父 POM。
- **除 admin-dependence 外，任何模块 POM 里都不允许出现版本号。**
- 依赖链：`admin-dependence` ← `admin-common` ← `admin-log` ← `admin-permission` ← `admin-system` ← `admin-boot`；`admin-doc` 被 `admin-permission` 依赖。
- 只有 admin-boot 配置 spring-boot-maven-plugin 的 repackage；其余模块不打可执行包。

**两条关键约束（违反会直接编译或启动失败）：**

1. `admin-common` 是纯工具模块，不允许依赖任何其他业务模块，只允许依赖 admin-dependence 与第三方工具库。
2. `admin-log` 不能依赖 `admin-permission`，否则形成循环依赖。因此 admin-log 里的切面要拿"当前登录用户"，只能从 HTTP 请求属性里读（认证过滤器会把登录用户对象同时写入请求属性，属性名 `admin.loginUser`），**不允许**引用 admin-permission 里的 ThreadLocal 上下文类。

**常量归属（必须遵守）**：`admin.loginUser`、请求头名、Redis 键前缀、状态值、菜单类型值、超管角色编码 `admin`、MASK 占位符等全部常量，**只能定义在 admin-common 的 `com.ming.admin.common.constant` 包下**，供 admin-log 与 admin-permission 共同引用。禁止在两个模块里各写一份同义字符串常量，否则改一处会静默失效。

## 五、接口地址与请求头约定

后端接口地址**不使用 `/api` 前缀**。

**总约定：路径全小写、请求头名全小写。**

- 后端映射注解里的路径、数据库里按钮的 perms、前端按钮权限指令里的字符串，三处一律全小写。
- 所有自定义请求头（traceId、token、语言）一律用小写形式书写。
- 理由：URL 路径大小写敏感，只要一处写 `sysUser`、另一处写 `sysuser`，权限就会静默失效（接口全部 200007 且不报错）；全小写从源头消除这个风险。HTTP 头名本身大小写不敏感，统一小写只是为了避免出现两种写法。

### 5.1 命名规则

Controller 的类路径与方法路径写在 Spring 的映射注解里，命名遵循以下规则：

1. 取 Controller 类的全限定名，去掉根前缀 `com.ming.`。
2. 去掉路径中出现的 `controller` 包段（整段删除，不留下多余斜杠）。
3. 去掉类名结尾的 `Controller` 后缀。
4. 剩余部分（包路径 + 类名）**整段转全小写**，`.` 替换为 `/`，前面补 `/`，作为**类级路径**。
5. 方法名**转全小写**后作为**方法级路径**，前面加 `/`。

也就是 `SysUser` 变成 `sysuser`、`resetPassword` 变成 `resetpassword`。`Sys` 前缀不省，只是跟着转小写。代码里的类名与方法名照常写驼峰（`SysUserController`、`resetPassword`），只有 URL 用小写形式。

示例：

| 类与方法 | 类级路径 | 方法级路径 | 完整地址 |
|---|---|---|---|
| `com.ming.admin.system.controller.SysAuthController#login` | `/admin/system/sysauth` | `/login` | `/admin/system/sysauth/login` |
| `com.ming.admin.system.controller.SysUserController#page` | `/admin/system/sysuser` | `/page` | `/admin/system/sysuser/page` |
| `com.ming.admin.system.controller.SysUserController#resetPassword` | `/admin/system/sysuser` | `/resetpassword` | `/admin/system/sysuser/resetpassword` |
| `com.ming.admin.system.controller.SysMenuController#tree` | `/admin/system/sysmenu` | `/tree` | `/admin/system/sysmenu/tree` |

**路径里不允许出现任何大写字母**，这是硬性要求。

### 5.2 实现要求

- 路径照常写在 Spring 映射注解里：**类级**写类路径前缀，**方法级**写方法路径，二者拼接结果必须等于 5.1 推导出的地址。
- **不要**引入自定义请求映射处理器或任何路径自动生成机制，就用 Spring 原生写法。
- 认证过滤器与权限拦截器解析"请求地址"时，取 Spring MVC 的最佳匹配模板路径（类级路径 + 方法级路径的拼接结果），拿不到时回退为去掉上下文路径的请求 URI。这样解析结果与映射注解里写的路径天然一致，权限标识不会跑偏。
- 所有接口一律 POST，方法上只标注 POST 映射注解。
- 应用**不设置** `server.servlet.context-path`；将来若需要额外前缀，由网关承担，代码不动。
- 在 admin-boot 里加一个启动扫描组件：遍历 Spring MVC 注册的全部处理器方法，收集每个方法的实际路径，同时收集带权限标识注解的方法与其权限标识（供 12.4 的清单接口使用）。路径与 5.1 规则逐条比对，不符合规则的用 WARN 日志列出来（只警告、不阻断启动，避免误伤文档与静态资源路径）。扫描结果缓存到内存，不要每次请求都重新扫。

### 5.3 前端与网关

- 前端所有请求统一以 `/api` 开头，这个前缀**只由 axios 实例的 baseURL 提供**，业务请求代码里写的路径不带 `/api`。
- 开发环境由 Vite 代理把 `/api` 转发到 `http://localhost:8080` 并**去掉 `/api` 前缀**。
- 将来接入网关后，由网关负责剥离 `/api`，前端代码不需要改动。因此 `/api` 不允许散落在业务请求代码中。
- 开发环境走 Vite 代理，属于同源请求，应用**不需要**配置 CORS；生产环境若前后端不同源，由网关统一处理并**逐条列出允许的来源**，禁止使用 `*`。应用自身不要写 `@CrossOrigin` 或在 Web 配置里放开通配来源。

## 六、统一返回与状态码

### 6.1 统一返回体

所有 Controller 方法（无例外）返回统一返回体对象，泛型参数是业务数据类型。字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| code | Integer | 是 | 状态码，**200 表示成功** |
| message | String | 否 | **调试用英文短语**，只给人看日志和接口调试用，**前端不得依赖它做展示**。成功时为 null |
| data | 泛型 | 否 | 业务数据；无数据时为 null。**参数校验失败时承载校验错误对象**（见 6.1.1） |
| timestamp | Long | 是 | 毫秒时间戳（返回前端时按第八章规则转为字符串） |

返回体只有 code、message、data、timestamp 四个字段：

- **追踪号不放在返回体里**：traceId 统一通过响应头 `x-trace-id` 与日志传递（见第九章）。
- **错误详情不放平级字段**：参数校验的 field、reason 一律装进 `data` 里的专用对象（见 6.1.1）。

静态工厂方法至少提供：成功（无数据）、成功（带数据）、失败（按状态码）、失败（按状态码 + 调试消息）、失败（按状态码 + 校验错误对象）。

**前端只依赖 code 与 data。** 这是硬约定：后端可以随时调整 message 文案而不影响前端任何一行代码。message 的用途是让开发者看响应、看日志时立刻知道发生了什么，例如 `Validation failed for field 'username'`、`Invalid credentials`、`Access denied`；**凡是需要展示给用户看的文案，一律由前端按 code（以及校验失败时的 field + reason）翻译**。

**message 的取值规则**：

| 场景 | message | data |
|---|---|---|
| 成功 | null | 业务数据 |
| 参数校验失败（100004） | `Validation failed for field '{字段名}'` | 校验错误对象（见 6.1.1） |
| 其余任何失败 | 一句固定的英文短语，按错误码一一对应硬编码在后端（例如无效凭证、账号已禁用、无权限、系统异常），**不拼接用户输入、不做国际化** | null |

### 6.1.1 校验错误对象（放在 data 里）

`data` 是一个专用对象，**只有两个字段**：

| 字段 | 类型 | 说明 | 示例 |
|---|---|---|---|
| field | String | 出错字段名，**归一化**后的形式（剥掉嵌套索引与路径） | `username`、`roleIds` |
| reason | String | 校验原因，取自 **7.2 的受控词表**，前端用它取文案 | `required`、`len`、`pattern`、`email` |

响应示例：

```json
{
  "code": 100004,
  "message": "Validation failed for field 'username'",
  "data": { "field": "username", "reason": "required" },
  "timestamp": "1735689600000"
}
```

前端取文案的规则（详见 19.2）：用 `field.{field}` 的词条与 `validation.{reason}` 的词条拼成一句，例如「用户名」+「不能为空」；拼不出词条时退回 `error.100004`。

**只返回第一个错误**：`data` 是单个对象，不是数组。原因见 7.1，`reason` 的取值见 7.2。

**为什么单独建模一个类**：这个对象要有独立的类（放在 admin-permission 的 `com.ming.admin.common.response` 包下），由全局异常处理器构造并塞进统一返回体的 data。不要用 Map 或 JSON 字符串拼装 —— 类型明确才能让接口文档、前端类型生成、日志三处都对得上。

**HTTP 状态码约定：永远返回 HTTP 200**，业务状态一律放在 body 的 code 字段里。包括认证失败、无权限，也要用 HTTP 200 + body code 返回，避免前端 axios 走 HTTP 异常分支。

### 6.2 状态码分段

状态码按**前三位分类**，全部业务码统一 6 位：

| 号段 | 分类 |
|---|---|
| 200 | 成功（唯一的成功码） |
| 100xxx | 公共（参数、请求格式、系统级异常） |
| 200xxx | 业务（认证与权限、用户、角色、菜单全部收在这个号段） |

业务码只有 100xxx 与 200xxx 两个号段，不按业务模块划分号段。前端判定只看 `code === 200`，不做号段推断，因此号段只表达"公共 / 业务"两层含义，具体错误一律以码表为准。

完整码表：

| code | 含义 |
|---|---|
| 200 | 成功 |
| 100004 | 参数校验失败 |
| 100005 | 请求体格式不正确 |
| 100006 | 请求方式不允许 |
| 100007 | 请求地址不存在 |
| 100008 | 系统异常 |
| 100009 | 日期格式不正确 |
| 100010 | 数据已存在或状态冲突 |
| 200003 | 未登录或登录已过期 |
| 200004 | 用户名已存在 |
| 200007 | 无访问权限 |
| 200008 | 用户不存在 |
| 200009 | 不能操作当前登录用户 |
| 200010 | 不能操作超级管理员账号 |
| 200011 | 原密码不正确 |
| 200012 | 角色编码已存在 |
| 200013 | 角色不存在 |
| 200014 | 该角色已被用户使用，不能删除 |
| 200015 | 用户名或密码错误 |
| 200016 | 账号已被禁用 |
| 200017 | 不能修改或删除内置超级管理员角色 |
| 200018 | 该菜单下存在子菜单，不能删除 |

码表里 200xxx 的**数值顺序不代表模块分组**（200003 与 200015 都属于认证），不要试图按模块重新排列：权限标识、前端词条、SQL 与文档里到处都引用这些数字，重排没有任何收益。

后端只返回数字码、一句调试用英文短语，以及校验失败时的 field + reason；**不做后端国际化**，也**不生成面向用户的句子**；中文/英文文案全部由前端 vue-i18n 按 `error.{code}`（参数校验失败时按 field + reason 组合）翻译。

前端判定规则：`code === 200` 即成功，其余一律视为失败。

## 七、参数校验与异常处理

- 所有业务接口入参从请求体取，用校验注解触发校验。
- 新增与修改用校验分组（Create 分组、Update 分组），避免"新增要密码、修改不要密码"这类冲突。
- 校验注解的 message **只写 7.2 受控词表里的 reason 值**（`required`、`len`、`pattern`、`email`、`range`、`type` 六个之一），不要写中文、不要写英文句子，**也不要自创原因值**。这个值会被全局异常处理器原样放进校验错误对象的 `reason` 字段，前端按 19.2 的规则拼成完整文案；**注意它不会进入返回体的 message 字段**，message 是调试短语。
- **状态与类型字段一律用 `Integer` 接收**并做取值校验（例如 status 只允许 0 或 1、type 只允许 1/2/3），禁止用 `Boolean` 或 `String` 接收。原因：前端表单控件的值可能是 `0`、`"0"`、`false` 三种形态，用 Boolean 或 String 接收会在"禁用"这种零值场景下判断错乱。
- 全局异常处理必须覆盖：业务异常、请求体校验失败、请求体不可读（JSON 格式错）、参数类型不匹配、请求方法不支持、404、日期解析失败、以及兜底 Exception。
- 业务异常和校验异常返回对应状态码，兜底异常返回 100008 并记录完整堆栈，**不把堆栈信息返回给前端**。
- 日期解析失败必须返回 **100009**，而不是笼统的 100005。自定义日期反序列化器内部抛业务异常时，全局处理器要在包装异常（请求体不可读异常）里识别并还原该状态码。
- 请求体大小走 Spring Boot 默认限制即可，不额外放开。

### 7.1 参数校验只返回第一个错误（**必须按此实现**）

参数校验失败统一返回 **100004**，并且**只返回一条错误**。错误详情放在 **data** 里的校验错误对象中（结构见 6.1.1）：

| 位置 | 内容 | 示例 |
|---|---|---|
| code | 固定 100004 | `100004` |
| message | 调试短语，含字段名，仅供排查 | `Validation failed for field 'username'` |
| data.field | 出错字段名，**归一化**后的形式 | `username`、`roleIds` |
| data.reason | 校验原因，取自 7.2 受控词表 | `required`、`len` |

**为什么可以只返回第一个**：前端表单在提交前会做完整的必填与格式校验（VeeValidate + yup），用户正常情况下一次性就能看到所有问题；后端只返回第一条是**兜底防线**，用来防止绕过前端或双方规则不一致时的脏数据入库，不需要承担"一次列全"的职责。因此 data 是单个对象而不是数组，前后端处理都更简单。

**实现要点（必须满足，否则体验会退化）：**

1. **顺序稳定**：一次请求可能有多个字段校验失败，必须取"稳定的第一个"，不能拿 Map 迭代顺序去碰运气，否则同一份错误数据每次返回的字段都可能变。做法：按 DTO 字段声明顺序收集错误（用 LinkedHashMap 或直接遍历字段列表取首个），并让 DTO 字段声明顺序与表单从上到下的顺序一致，这样提示位置也最自然。
2. **字段名归一化**：嵌套字段把索引与路径剥掉，只留最后一段字段名。例如 `roleIds[0]` → `roleIds`、`user.username` → `username`。前端拿到的必须能与表单项的名字（Element Plus 表单的 prop）精确对上。
3. **不返回用户提交的原值**：data 里只有 field 与 reason 两个字段，不回显任何输入值。原因有二：一是密码这类字段会顺着错误对象流到前端提示、日志、控制台，属于信息泄露；二是日期类型在序列化时容易抛异常。这条要严格执行。
4. **日志留痕**：校验失败时后端打一条 WARN 日志，包含字段名、reason、请求地址与 traceId，便于排查。日志里**不要**打印字段原值（密码、手机号等敏感内容）。
5. **前端配合**：
   - 收到 100004 时用 `data.field` 定位到对应表单项：设置该表单项的 error（文案由 field + reason 拼出）并滚动聚焦过去，让用户一眼看到问题所在；
   - 兜底场景（后端返回的 field 在前端表单里找不到对应控件）退化为一条页面级提示，不要报错；
   - 表单单次提交只会返回一条错误，前端的完整校验必须真的执行，不要依赖后端逐条返回。
6. 其他异常（100005、100009、404、100008 等）**data 为空**，前端按 `error.{code}` 提示；日期格式这一类天然只有一个错，不需要单独建模。

### 7.2 校验原因受控词表（**reason 只允许取这六个值**）

后端的校验注解 message **只能**从下表取一个值。前端按 `validation.{reason}` 配词条，因此这张表就是前后端之间的契约：

| reason | 适用注解 | 中文 | 英文 |
|---|---|---|---|
| required | @NotNull、@NotBlank、@NotEmpty | 不能为空 | is required |
| len | @Size、@Length | 长度不符合要求 | has an invalid length |
| pattern | @Pattern | 格式不正确 | has an invalid format |
| email | @Email | 邮箱格式不正确 | is not a valid email |
| range | @Min、@Max、@DecimalMin、@DecimalMax | 超出允许范围 | is out of range |
| type | 自定义类型校验（例如状态、菜单类型取值） | 取值不合法 | has an invalid value |

约定与红线：

- **禁止自创 reason**。所有校验注解的 message 都必须落在上表内；确实需要整句特例时，用 19.2 的 `validation.{field}.{reason}` 键表达（例如 `validation.username.required` = 请输入用户名），而不是发明新的 reason。
- 上表新增任何一个值，都要同步改前端词条与 7.3 的清单比对逻辑，属于"改契约"，不是随手加常量。
- 7.3 的清单接口导出的 reason 必须全部来自这张表；启动扫描发现词表外的 reason 时打 WARN 日志列出来。

### 7.3 校验规则清单接口（**防止前端漏配词条**）

后端在启动时扫描全部 DTO 的校验注解，导出"字段名 + 原因"清单，通过接口暴露给前端（只校验登录）：

- 地址：`/admin/system/sysmenu/rules`
- 出参：数组，每项含 `field`（DTO 字段名）、`reason`（受控词表值）、`labelKey`（建议的字段标签键名，即 `field.{field}`）
- 与权限标识清单一样在启动扫描组件里一次性收集并缓存到内存，不要每次请求重新反射扫描

**前端必须这样用它**：在**开发环境下**启动时拉一次清单，与本地 `field.*` 标签词条、`validation.*` 原因词条比对，缺哪条就在浏览器控制台打 WARN 列出来（形如 `missing i18n key: field.roleIds`）。生产环境不请求、不输出。

这条机制解决的是这类问题：后端新增了一个带 @NotBlank 的字段，前端没配 `field.xxx` 词条，用户就会看到「不能为空」这种缺少主语的提示、甚至看到 `xxx` 这种代号。有了清单，这种漏配在开发阶段就会暴露，而不是等用户报障。

### 7.4 分页

- 分页请求对象提供：页码（默认 1）、每页条数（默认 10，最大 100）、关键字、排序字段、排序方向，其余业务过滤字段由各自的请求对象继承后追加。
- 分页返回对象提供：数据列表、总条数、当前页、每页条数、总页数。
- 分页由 MyBatis-Plus 分页插件实现，插件在配置类里注册，并设置单页上限。
- 注意：总条数是 Long，按第八章规则会序列化成字符串，前端需要转成数字后再交给分页组件。

### 7.5 排序字段安全（**必须实现，不要用用户输入直接拼 order by**）

- 每个列表页的 DTO 自己声明**允许排序的字段白名单**：一份"前端字段名 → 数据库列名"的映射，写在对应 DTO 或该模块的常量里。
- Service 拼排序时只使用白名单映射后的列名，**严禁**把请求里的字符串直接传给 orderBy。
- 排序方向只接受 `asc` 与 `desc`（忽略大小写），其他值一律回落到默认排序。
- 排序字段为空、不在白名单、或映射后为空 → **回落到该列表的默认排序**（例如 `create_time desc, id desc`），不报错、不返回 500。
- 前端的排序下拉选项直接由这份白名单渲染，前后端字段名保持一致。
- 验收时必须验证：排序字段传 `id; drop table sys_user`、传不存在的列名，接口仍正常返回 200（回落默认排序），数据库无异常。

## 八、日期与 JSON 序列化约定

一套全局 Jackson 配置集中实现（配置类放在 admin-permission 的 config 包），业务代码里不写任何序列化注解。

### 8.1 类型约定

- 所有日期字段统一用 `java.util.Date`，**不要用** LocalDateTime、LocalDate、Instant。
- 数据库时间列用 datetime，连接串明确时区（见第二十四章），服务器与应用时区保持一致。

### 8.2 序列化（后端 → 前端）

- 日期类型序列化为**毫秒时间戳（数字）**。
- 所有 `Long` 与 `long` 类型序列化为**字符串**（防止前端精度丢失）。这条对分页的总条数、`timestamp` 字段、以及所有 `id`、`createBy`、`updateBy` 字段同样生效，前端按需转成数字。
- 其余类型保持默认行为。
- 注意日期与 Long 是两条独立规则：日期输出数字（走日期序列化器），Long 字段输出字符串（走 Long 序列化器）。不要为了统一而把日期也变成字符串。

### 8.3 反序列化（前端 → 后端）

自定义日期反序列化器，按以下顺序判断：

1. JSON 值是数字，或字符串内容是纯数字 → 按毫秒时间戳 `new Date(值)`。
2. 字符串长度为 10（`yyyy-MM-dd`）→ 按 `yyyy-MM-dd` 解析。
3. 其他字符串 → 按 `yyyy-MM-dd HH:mm:ss` 解析。
4. 解析失败或格式不符 → 抛出业务异常，状态码 **100009 日期格式不正确**。
5. 空值 → null。

`Long` 字段要能同时接受 JSON 数字与字符串（前端一律传字符串）。

**这条规则同时作用于 Redis 中的对象**：登录用户对象按同一套配置序列化后存 Redis，因此其中的 `id` 在 JSON 里也是字符串；反序列化回对象时必须能同时接受字符串与数字，否则认证过滤器在读取时会失败。写代码时请显式确认这一点（用同一套 ObjectMapper，不要另建一个）。

## 九、traceId 链路

前后端共用请求头 `x-trace-id`（全小写）。

**前端**：每次请求发起前生成一个 traceId（32 位无横线，用浏览器随机 UUID 能力），放进请求头；响应回来后从响应头再读一次，错误日志里带上它，方便与后端日志对账。

**后端**：

1. 在最外层注册一个 traceId 过滤器，优先级**高于**认证过滤器。
2. 读请求头 `x-trace-id`；为空则用 admin-common 的 ID 工具生成 32 位无横线 UUID。
3. 写入三处：日志 MDC（键名 `traceId`）、请求属性、**响应头 `x-trace-id`**。
4. 响应头的写入放在过滤器的 finally 里，保证 404、异常、未认证等任何分支也能拿到 traceId。
5. 请求结束后清理 MDC。
6. 只写响应头（见 6.1）。需要按 traceId 排查时看响应头与日志。
7. logback 输出格式必须包含 traceId，保证一次请求的所有日志能串起来。

**跨线程提醒**：MDC 不会自动跨线程传递。审计日志、异步任务、Spring 的 `@Async` 方法内部拿不到父线程的 MDC，需要显式透传（把 traceId 作为参数传入，或使用 MDC 的跨线程包装）。不要在异步方法里假设 MDC 还有值。

## 十、认证与鉴权机制

这是本系统最核心的部分，请严格按下面实现。

### 10.1 登录流程

1. 前端把用户名、密码以请求体 POST 给登录接口。
2. 后端按用户名查用户（含已逻辑删除过滤）。查不到返回 200015。
3. 状态为禁用返回 200016。
4. 用 Argon2id 校验密码，不匹配返回 200015。
5. 生成 tokenId：**32 位无横线的小写 UUID 字符串**，由 admin-common 的 ID 工具生成。
6. 组装登录用户对象（用户 ID、用户名、昵称、是否超级管理员、角色编码列表、登录时间、登录 IP、User-Agent），序列化为 JSON 存入 Redis。
7. Redis 键规则：`admin:token:{tokenId}`，值为登录用户 JSON，过期时间取配置项，默认 2 小时。
8. 返回 tokenId 与过期秒数。**绝不能返回密码或密码哈希**。

说明：同一账号允许多端同时在线，各自持有独立 tokenId，互不影响（不做单点互斥）。

### 10.2 滑动续期

认证过滤器每次校验通过后，检查该 token 键的剩余过期时间；**仅当剩余时间小于配置时长的一半时才重置为完整时长**，避免每个请求都写一次 Redis。默认时长 2 小时。

### 10.3 前端携带方式

请求头 `authorization`（全小写），值为 `Bearer ` 加 tokenId。后端解析时兼容不带 `Bearer ` 前缀的裸 tokenId。同时兼容名为 `token` 的自定义请求头。

### 10.4 认证过滤器（这是"如果为空直接返回"的那一环）

位置：admin-permission 的 security.filter 包，继承 Spring 的 OncePerRequestFilter，注册为高优先级过滤器 Bean（排在 traceId 过滤器之后）。

执行顺序：

1. 若是跨域预检请求（OPTIONS），直接放行。
2. 命中白名单直接放行。白名单：登录接口、登出接口、接口文档相关路径、swagger 资源路径、favicon、error 路径、静态资源。
3. 从请求头取 token（先去 `Bearer ` 前缀，去掉空白）。为空则写 200003 响应并**立即结束**，不再进入后续链路。
4. 用 tokenId 去 Redis 取登录用户 JSON。
5. 取不到（过期或已登出）同样写 200003 响应并结束。
6. 反序列化成登录用户对象，做两件事：写入线程上下文（ThreadLocal）；写入请求属性 `admin.loginUser`。
7. 执行滑动续期。
8. 放行。用 try/finally 保证请求结束后清理线程上下文。
9. 响应必须是 HTTP 200 + 统一返回体，Content-Type 为 JSON 且字符集 UTF-8。

线程上下文用普通 ThreadLocal 即可，但要保证 finally 清理，避免线程池复用导致的串号。

**白名单路径清单（写成常量，不要散落字符串）**：登录接口 `/admin/system/sysauth/login`、登出接口 `/admin/system/sysauth/logout`、`/doc.html`、`/webjars/**`、`/v3/api-docs/**`、`/swagger-ui/**`、`/swagger-resources/**`、`/favicon.ico`、`/error`、`/error/**`、静态资源（`/static/**`、`*.css`、`*.js`、`*.png` 等，具体按实际资源目录收敛）。最后一条兜底：白名单**不做通配前缀放行**，只允许上述明确列出的路径，禁止图省事放行 `/admin/**`。

### 10.5 权限注解

自定义注解名 `Menu`，只能标注在方法上，运行期保留，只有一个可空字符串属性 value。

权限标识判定规则（**必须严格按此实现**）：

1. 方法上完全没有该注解 → 只校验登录态，不校验权限。**只用于**：登录、登出、`me`、工作台统计、各模块的 `detail` 详情接口、以及被多个页面共用的下拉、树、清单接口（`role/list`、`menu/list`、`menu/perms`、`role/menuIds`）。
2. 注解 value 为空 → 权限标识 = **该接口的请求地址**（即第五章的地址）。**这是默认用法，所有需要鉴权的接口都这么写，不需要填值。**
3. 注解 value 有值 → 权限标识就是该值。**只在两个不同的接口需要共用同一个权限时才这么写。**
4. 非 Controller 方法（静态资源等）直接放行。

**摆放位置强制要求**：该注解只允许标注在 **Controller 的方法**上。标到 Service 上不会生效（拦截器只看 HandlerMethod），会造成"以为鉴权了其实没鉴权"的安全漏洞。请在第十四章的业务实现里逐个接口确认。

注意：接口地址已经由类级与方法级的映射注解确定，所以需要鉴权的接口上只标注这个注解、不写值即可，不要重复抄一遍地址。

### 10.6 权限拦截器（这是"判断当前用户是否有这个权限"的那一环）

位置：admin-permission 的 security.interceptor 包，实现 Spring 的 HandlerInterceptor，在 Web 配置类里注册，拦截 `/admin/**`，排除白名单。

执行逻辑：

1. 若非 HandlerMethod，放行。
2. 按 10.5 规则解析出权限标识。为空则放行。
3. 从线程上下文取登录用户，取不到返回 200003（正常情况下认证过滤器已挡住，这里是双保险）。
4. 若登录用户是超级管理员（`superAdmin` 为真），直接放行。
5. 取该用户的权限标识集合（见 10.7），包含当前权限标识则放行。
6. 否则返回 200007 统一返回体。同样使用 HTTP 200 + body code 的方式写回，并终止后续处理。

### 10.7 用户权限集合与缓存

- 权限集合来源：用户 → 用户角色关联 → **仅状态为启用的角色** → 角色菜单关联 → 菜单行的权限标识字段（非空去重）。
- **只统计启用状态、未逻辑删除的菜单，以及启用状态的角色**。被禁用的角色不贡献任何权限与菜单（数据保留，恢复启用即生效）。
- 缓存到 Redis，键 `admin:perm:{userId}`，默认 30 分钟。用 Redisson 的集合结构存储。
- **缓存失效用版本号方案**：缓存键实际写成 `admin:perm:{userId}:{permVersion}`，另有一个全局键 `admin:perm:version` 存当前版本号。凡是影响权限的写操作（角色分配菜单、菜单增删改、用户分配角色、角色增删改与启停、菜单启停），只做一件事：`INCR admin:perm:version`。旧键因不再被读取而在 30 分钟后自然过期。
  - 理由：按用户逐个删缓存容易漏删；`KEYS` 扫描在生产环境会阻塞 Redis。版本号自增一次即可让全部旧缓存失效。
  - 该版本号自增方法放在 admin-permission 的缓存服务里，业务代码调用它，不要自己拼键名。
- **超级管理员判定**：登录时查出该用户所有角色的编码（只取启用角色），只要包含 `admin` 就标记为超级管理员，写入登录用户对象。超级管理员在拦截器里直接放行，前端拿到 `superAdmin` 布尔值与展示用的 `*:*:*`。
- 登录用户对象里同时保留 `superAdmin` 布尔值与权限集合，两者不要互相推断：**判据永远只看 `superAdmin`**。

### 10.8 登出

登出接口删除 Redis 中的 token 键并清理上下文。前端同时清除本地存储。登出接口在白名单里，因此**必须自己校验 token 是否存在**：token 无效时也返回成功，不报错。

不做以下功能（明确排除）：图形验证码、登录失败次数锁定、单点登录互斥、多端在线管理。

### 10.9 密码存储

- 算法 Argon2id，**封装在 admin-common**（对外暴露编码与校验两个静态方法，内部持有唯一编码器实例，全项目只在这里构造）。
- 参数固定为：salt 长度 16 字节，输出哈希长度 32 字节，并行度 1，内存 19456 KiB（19 MiB），迭代次数 2。这是 OWASP 推荐档位。
- 密码强度规则：长度 8 到 32，至少包含字母和数字。校验注解正则写在 DTO 上。
- 种子数据里超级管理员的密码哈希见第二十五章，**直接使用，不要自己编造哈希，也不要改成明文**。
- 密码字段**只进不出**：不进入任何 VO，不进入 `me` 返回，不进入日志，不进入审计记录的 params（见 22.2 脱敏）。

## 十一、数据库设计

数据库名 `admin`，字符集 utf8mb4，排序规则 utf8mb4_general_ci，引擎 InnoDB。所有表带逻辑删除字段与审计字段。

**名称字段只保留一个：不要任何 `_en` 之类的多语言字段，用户填什么就显示什么。** 国际化只针对界面固定文案，不针对业务数据。

**表名与类名的对应关系（约定直接映射，实体上不写表名注解）**：表名下划线转驼峰就是实体名，不做表前缀剥离；Mapper、Service、Controller、DTO、VO 都在实体名基础上加后缀，前缀一律不省。

| 表名 | 实体 | Mapper | Service | Controller | 接口地址前缀 |
|---|---|---|---|---|---|
| sys_user | SysUser | SysUserMapper | SysUserService | SysUserController | `/admin/system/sysuser` |
| sys_role | SysRole | SysRoleMapper | SysRoleService | SysRoleController | `/admin/system/sysrole` |
| sys_menu | SysMenu | SysMenuMapper | SysMenuService | SysMenuController | `/admin/system/sysmenu` |
| sys_user_role | SysUserRole | SysUserRoleMapper | （无独立 Service，由用户服务维护） | — | 无 |
| sys_role_menu | SysRoleMenu | SysRoleMenuMapper | （同上，由角色服务维护） | — | 无 |
| sys_operation_log | SysOperationLog | SysOperationLogMapper | SysOperationLogService | — | 无（本次不做查询接口） |

认证模块没有对应的表，Controller 命名为 `SysAuthController`，地址前缀 `/admin/system/sysauth`。

前缀一律带 `Sys`，因为将来还会出现别的类型的用户、角色、菜单表（例如前台用户），不带前缀必然撞名。接口地址同样保留这个前缀，只是**整段转小写**（见 5.1）。

### 11.1 用户表 sys_user

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | bigint | 主键自增 | |
| username | varchar(50) | 非空，唯一索引 | 登录名 |
| password | varchar(255) | 非空 | Argon2id 哈希 |
| nickname | varchar(50) | 非空 | 显示名 |
| email | varchar(100) | 可空 | |
| phone | varchar(20) | 可空 | |
| avatar | varchar(255) | 可空 | 头像地址 |
| status | tinyint | 非空，默认 1 | 1 启用 0 禁用 |
| remark | varchar(255) | 可空 | |
| create_by / create_time / update_by / update_time | | | 审计字段 |
| deleted | tinyint | 非空，默认 0 | 逻辑删除 |

索引：username **唯一索引（单列，不加 deleted）**；status 普通索引。

**username 唯一性的完整语义（必须照此实现）：**

- 唯一索引就是 `username` 单列，**不要**改成 `(username, deleted)` 之类的组合索引。
- **逻辑删除后用户名永久不可复用**：删除测试账号 `test` 之后，再也不能新建 `test`。这是刻意设计——用户名是对外可见的标识，历史日志、审计记录、外部对接都引用它，复用会导致"这个人是谁"永久无法追溯。
- 因此重名校验的判定范围是**全部记录（含已逻辑删除）**：
  1. 新增或修改用户名时，查该 username 是否存在（**不加 deleted 过滤**）；
  2. 只要存在（无论是否已删除），一律返回 **200004 用户名已存在**；
  3. 前端在新增用户弹窗对 200004 给出明确提示（词条文案要说明"该用户名曾使用过、不可复用"，不要只说"已存在"让人反复试）。
- 因为校验覆盖全部记录，正常情况下不会触发数据库唯一索引冲突；出于兜底，插入/更新时捕获唯一约束异常并转成 200004，不要把 100008 系统异常抛给用户。
- 不提供"修改用户名"，也不提供回收站/恢复已删除用户功能。

为什么不采用其他方案：把已删除记录的 username 改写成 `test_deleted_{id}` 能腾出名字，但会污染历史数据的可读性，且与审计、日志里的用户名对不上；用 `(username, deleted)` 组合唯一索引更糟——它允许存在多条同名已删除记录，一旦恢复或排查就会歧义。**单列唯一 + 永不复用，是唯一不会产生历史歧义的方案。**

## 十二、权限模型（最容易理解错，请仔细读）

菜单表一张表承担三件事：侧边栏/路由展示、接口权限点、按钮权限点。

| 类型 | perms 怎么填 | 作用 |
|---|---|---|
| 1 目录 | **留空** | 只做侧边栏分组，并通过"角色是否关联该行"控制整块是否可见。目录下有没有菜单由子节点体现 |
| 2 菜单 | **留空** | 只代表一个页面入口，角色关联了该行侧边栏才出现这个页面，不贡献任何权限 |
| 3 按钮 | **必填** | 值等于对应接口的地址，既决定接口能否调用，也决定前端按钮是否渲染 |

### 12.1 三条彼此独立的规则

1. **页面/目录是否展示** = 该用户角色是否关联了对应的目录/菜单行。与 perms 无关。
2. **接口能否调用** = 接口上标了权限注解，且用户权限集合包含解析出的权限标识。
3. **按钮是否渲染** = 用户权限集合包含该按钮的权限标识。

"perms 为空的菜单行不贡献任何权限"，所以目录与菜单行天然只承担展示职责 —— 这就是需求里"权限为空的用来控制页面是否展示"的含义。

**超级管理员的例外**：以上三条判断对超级管理员全部豁免——后端拦截器直接放行，前端 `v-has` 与权限判断函数直接通过。判据是 `superAdmin` 布尔值（见 1.2 与 10.7）。

### 12.2 查询也是一个权限点

**列表查询接口必须鉴权**，对应的权限点就是每个页面下的「查询」按钮。这样才做得到"没勾查询就查不了数据"。

前端配套处理：页面的搜索按钮用同一个权限标识包裹，没勾选时**按钮也不渲染**（用户进去只看到查询条件与一张空表格），后端接口同时返回 200007，两头都拦，不会出现"点了搜索才报错"的糟糕体验。

因此每个页面下的按钮清单为：

| 页面 | 按钮权限点（perms 一律等于对应接口地址） |
|---|---|
| 用户管理 | 查询、新增、编辑、删除、重置密码、启用/禁用、分配角色 |
| 角色管理 | 查询、新增、编辑、删除、分配权限 |
| 菜单管理 | 查询、新增、编辑、删除 |

### 12.3 不鉴权的接口

以下接口只校验登录态，不参与权限控制，因为它们是页面运行的基础数据或与具体按钮解耦：

- 登录、登出、`me`、工作台统计 `/admin/system/sysauth/count`
- 各模块的 `detail` 详情接口（依赖列表拿到的 id）
- 被多个页面共用的下拉、树与清单接口：`/admin/system/sysrole/list`、`/admin/system/sysmenu/list`、`/admin/system/sysmenu/perms`、`/admin/system/sysmenu/rules`、`/admin/system/sysrole/menuids`

### 12.4 权限标识清单接口（消灭手抄地址）

后端在启动时扫描所有带权限标识注解的处理器方法，收集成一份"权限标识清单"，每个条目包含三样东西：权限标识（即小写的接口地址）、所属模块（类路径末端，如 `sysuser`）、动作名（方法名转小写，如 `resetpassword`）。通过菜单模块的清单接口暴露给前端（只校验登录）。

菜单管理页新增或编辑按钮时，权限标识字段用这份清单做**下拉选择**，选中后按动作名自动带出按钮名称（按钮名的中英文由前端 i18n 按动作名翻译，例如 create 对应"新增"），用户仍可手动改名称。

这样配按钮时再也不需要人工抄写接口地址，从根上消除了"抄错地址导致接口 200007"这一类问题。清单里没有需要的标识时（例如两个接口共用一个权限），仍然允许手动输入。

**启动扫描同时产出第二份清单：校验规则清单**（字段名 + reason + 标签键），通过 `/admin/system/sysmenu/rules` 暴露，供前端开发期比对词条，见 7.3。两份清单都在同一个启动扫描组件里一次性收集并缓存到内存，两者的接口都只校验登录。

### 12.5 权限标识 = 接口地址带来的风险

权限标识默认等于接口地址，而接口地址写在映射注解里，所以**改类路径、改方法路径**都会静默导致数据库里的 perms 失效（接口全部变 200007，且不报错）。请在 admin-boot 加一个启动校验：扫描全部带权限注解的处理器方法，导出权限标识清单；开发环境下与数据库中已配置的 perms 比对，发现"数据库里有、代码里没有"的标识时打 WARN 日志列出，便于对账。生产环境只记录不阻断。

该比对**由配置开关控制**（默认 dev 开启、prod 关闭），比对时容忍数据库表中的 perms 为空或已删除的行。

**接口地址一旦上线就当作对外契约，不要随意改名。** 这条要写进 README。

## 十三、接口清单

所有接口一律 POST，参数一律从请求体取，不允许出现 GET 业务接口，不允许用查询参数或路径变量传业务参数。

地址按第五章规则书写。**前端请求时由 baseURL 统一加 `/api` 前缀，下表列出的是去掉该前缀后的后端真实地址。**

三条全局约定，写代码时不要各自发挥：

1. **批量删除入参一律叫 `ids`（数组）**，所有模块（含菜单）都一致，即使当前只有一条也传数组。前端做单条删除时传单元素数组即可，后端只实现一个批量入口。
2. 出参里的 `id`、`createBy`、`updateBy` 等 Long 字段，前端**一律按字符串**处理；需要比较时统一转字符串比较，避免精度问题。
3. 所有 VO 与 `me` 返回中都**不含** password 字段。

### 13.1 认证模块

| 接口 | 入参 | 出参 | 权限注解 |
|---|---|---|---|
| `/admin/system/sysauth/login` | username、password | tokenId、expiresIn（秒） | 无（白名单） |
| `/admin/system/sysauth/logout` | 无 | 无 | 无（白名单，内部自行校验 token） |
| `/admin/system/sysauth/me` | 无 | 见下 | 无（仅需登录） |
| `/admin/system/sysauth/count` | 无 | userCount、roleCount、menuCount | 无（仅需登录） |

`/admin/system/sysauth/me` 返回内容：

- user：用户基本信息（id、username、nickname、email、phone、avatar、status、roles 简要信息、createTime）
- roles：角色编码数组
- superAdmin：布尔
- perms：权限标识数组；超级管理员返回单元素数组 `*:*:*`（仅作展示与兼容，前端判断一律看 superAdmin）
- menus：该用户可见的菜单路由树（只含 type 1 和 2，只含启用状态的菜单，可见性字段一并返回供前端处理隐藏菜单）

菜单路由树节点字段：id、parentId、name、type、path、component、icon、sort、visible、keepAlive、redirect、children。

`/admin/system/sysauth/count` 是**工作台统计卡片专用接口**，只校验登录、不参与权限控制。理由见 21.2：列表接口带权限点，普通用户没有查询权限时工作台会拿不到总数甚至弹 200007。

### 13.2 用户管理

| 接口 | 入参关键字段 | 权限注解 |
|---|---|---|
| `/admin/system/sysuser/page` | 分页字段 + username、nickname、status、roleId | 有（不传值，权限标识即本地址） |
| `/admin/system/sysuser/detail` | id | 无（仅需登录） |
| `/admin/system/sysuser/create` | username、password、nickname、email、phone、status、roleIds、remark | 有（不传值） |
| `/admin/system/sysuser/update` | id + 基本信息（不含密码与角色） | 有（不传值） |
| `/admin/system/sysuser/delete` | ids（数组） | 有（不传值） |
| `/admin/system/sysuser/resetpassword` | id、newPassword | 有（不传值） |
| `/admin/system/sysuser/changestatus` | id、status | 有（不传值） |
| `/admin/system/sysuser/assignroles` | userId、roleIds | 有（不传值） |

业务约束：

- **用户名唯一且永不复用**，规则见 11.1；重名校验返回 200004。
- 不允许删除或禁用当前登录用户（200009）。
- 不允许删除超级管理员账号（200010）；不允许禁用超级管理员账号（同样返回 200010）。
- 删除为批量、逻辑删除，并同时清理用户角色关联；删除后清理受影响用户的权限缓存（走版本号自增）。
- **列表中混入超管自己**：不允许删除/禁用自己这条校验按 id 逐个判断，批量删除时只要包含当前用户或超管就整体拒绝，不要"删一半"。
- 用户列表查询需要带出角色信息（避免 N+1，用一次批量查询组装）。
- 分配角色时 `roleIds` 可为空数组（表示清空角色），但**创建用户时角色至少一个**（21.3），两者校验分组不同。
- 分配角色只接受启用状态的角色 id；传入已禁用或不存在的角色 id → 返回 200013。

### 13.3 角色管理

| 接口 | 入参关键字段 | 权限注解 |
|---|---|---|
| `/admin/system/sysrole/page` | 分页字段 + name、code、status | 有（不传值） |
| `/admin/system/sysrole/list` | 无（返回全部**启用**角色，供下拉选择） | 无（仅需登录） |
| `/admin/system/sysrole/detail` | id | 无（仅需登录） |
| `/admin/system/sysrole/create` | name、code、sort、status、remark | 有（不传值） |
| `/admin/system/sysrole/update` | id + 上述字段 | 有（不传值） |
| `/admin/system/sysrole/delete` | ids | 有（不传值） |
| `/admin/system/sysrole/menuids` | roleId | 无（仅需登录） |
| `/admin/system/sysrole/assignmenus` | roleId、menuIds | 有（不传值） |

业务约束：

- code 唯一；重名返回 200012。
- 内置超级管理员角色（code 为 `admin`）不允许删除、不允许改 code、不允许禁用，违规返回 200017。
- 角色下有用户时不允许删除，返回 200014。统计口径为**未逻辑删除的用户**。
- 分配菜单时先删旧关联再批量插入（id 先去重），并在事务内完成，完成后使权限缓存失效（版本号自增）。
- **角色启用状态变更（启用/禁用）后同样要使权限缓存失效**，因为禁用角色的权限必须立即消失。
- 删除角色时，如果 `sys_user_role` 里还有该角色的关联行，需一并清理（物理删除）。

**禁用角色的语义（必须照此实现）**：

- 禁用**不**解除角色与用户、与菜单的关联，配置数据全部保留；重新启用后立即恢复。
- 权限集合计算、`me` 的 perms 与 menus 生成，**都要排除已禁用的角色**。即：角色被禁用后，其下用户的权限与可见菜单立刻收缩。
- 因此校验用例：给 `common` 用户配好查询权限后，把 `common` 角色禁用，common 用户重新登录或等缓存失效后，用户管理列表接口返回 200007、侧边栏不再出现用户管理（超管不受影响）。

### 13.4 菜单管理

| 接口 | 入参关键字段 | 权限注解 |
|---|---|---|
| `/admin/system/sysmenu/tree` | 无（返回全量树，供管理页使用） | 有（不传值） |
| `/admin/system/sysmenu/list` | 无（返回全部启用菜单的树，供角色分配权限弹窗使用） | 无（仅需登录） |
| `/admin/system/sysmenu/perms` | 无（返回代码里全部可用的权限标识清单，供菜单表单的权限标识下拉使用） | 无（仅需登录） |
| `/admin/system/sysmenu/rules` | 无（返回全部 DTO 的校验规则清单：field、reason、labelKey，供前端开发期比对词条，见 7.3） | 无（仅需登录） |
| `/admin/system/sysmenu/detail` | id | 无（仅需登录） |
| `/admin/system/sysmenu/create` | parentId、name、type、path、component、icon、perms、sort、visible、keepAlive、redirect、status | 有（不传值） |
| `/admin/system/sysmenu/update` | id + 上述字段 | 有（不传值） |
| `/admin/system/sysmenu/delete` | ids（数组，与其他模块一致） | 有（不传值） |

业务约束：删除前逐个校验是否存在子菜单，任一有子节点即整体拒绝（200018）；parentId 不能指向自己或自己的子孙（200019）；层级类型约束见 11.3；perms 非空时做唯一性校验（200020，多条 perms 为空由唯一索引天然允许）；菜单树用内存递归构建，不要用递归 SQL。

菜单的增删改与启停都要使权限缓存失效（版本号自增）。菜单删除后，已存在的 `sys_role_menu` 关联行要一并物理清理。

### 13.5 通用信息接口（可选实现）

如无特殊需要，前端版本号可直接由构建期注入的环境变量提供，不必新增后端接口。若确实要做，才新增 `/admin/system/sysauth/info`，只校验登录；**不要**为了展示版本去读磁盘或扫描依赖。此接口非必需项。

## 十四、Service 层与持久层约定

### 14.1 命名规则

| 层 | 命名 | 示例 |
|---|---|---|
| 实体 | 表名驼峰 | `SysUser`（对应 sys_user） |
| Mapper | 实体名 + Mapper | `SysUserMapper` |
| Service | 实体名 + Service | `SysUserService` |
| Controller | 实体名 + Controller | `SysUserController` |
| DTO | 实体名 + 用途 + DTO | `SysUserPageDTO`、`SysUserSaveDTO` |
| VO | 实体名 + VO | `SysUserVO` |
| 转换器 | 实体名 + Converter | `SysUserConverter` |

**一律带 `Sys` 前缀，不要省。** 将来还会出现别的类型的菜单、角色、用户（例如前台用户），不带前缀必然撞名。

注意：Controller 类名带 `Sys`，接口地址同样保留这个前缀，只是**整段转成小写**，所以 `SysUserController` 对应的地址是 `/admin/system/sysuser`，`resetPassword` 方法对应 `/resetpassword`。

Service 继承 MyBatis-Plus 的 ServiceImpl，泛型用对应的 Mapper 与实体（例如 `ServiceImpl<SysUserMapper, SysUser>`）。

### 14.2 持久层全局配置（全部在代码配置类里声明）

在 admin-permission 的 MyBatis-Plus 配置类里用代码集中声明以下四项，实体上**不写任何 MyBatis-Plus 注解**（不写表名注解、主键注解、逻辑删除注解、字段注解）：

- 表名策略：下划线转驼峰自动映射，不剥离表前缀（实体名已带 Sys 前缀）。
- 主键策略：数据库自增。
- 审计字段自动填充：`create_time`、`update_time`、`create_by`、`update_by`，由统一的填充处理器从线程上下文取当前用户 ID 写入。
- 逻辑删除：字段名 `deleted`，已删值 1，未删值 0。

**配置位置**：逻辑删除、主键策略、表名策略、自动填充**全部只在这个代码配置类里声明**。`application.yml` 的 mybatis-plus 段只保留 Mapper 位置、实体包、SQL 日志实现，逻辑删除、主键策略、表名策略一律不在 yml 里声明——配置只有一个来源。

**审计字段填充的边界**：填充处理器从线程上下文取当前用户 ID，取不到时（例如登录接口、异步线程、无请求上下文）写 0 或 null，**不要报错**。系统内置数据与种子数据不依赖自动填充。

**逻辑删除为什么这么设计**：不用实体注解，而是集中在配置类里用代码声明，并且所有删除统一走一个封装好的删除方法（业务代码不允许自己拼更新语句去改 deleted 字段）。将来如果要换字段名、换取值、增加"删除人"、甚至改成物理删除，只改配置类与那个统一方法两处，业务代码一行都不用动。

### 14.3 其他约定

- **不分接口与实现两层**：每个业务模块只有一个 Service 类，放在 `com.ming.admin.system.service` 包下，**不建 service.impl 包**，类上直接标注 Spring 组件。
- 复杂查询写在 Service 里，用 Lambda 条件构造器拼装，不要写 XML。
- 多表写入方法加事务注解，回滚异常类型为 Exception。
- DTO/VO 与实体的转换用 MapStruct 转换器，转换器放在 `com.ming.admin.system.convert` 包。
- Controller 只做参数接收、权限注解标注、调用 Service、包装返回，**不允许写业务逻辑**。
- **每个需要鉴权的 Controller 方法都必须标注 `Menu` 注解**（见 10.5 的强制要求），并且逐个与 13 章的表格核对，不要漏标、也不要把该鉴权的接口标成不鉴权。

原因：本项目的权限标识默认等于接口地址，同一个地址要同时出现在三处（后端注解、数据库按钮的 perms、前端按钮权限指令）。前端这一处收敛之后，地址发生变更时就不会出现"后端改了、前端漏改，导致按钮不显示或接口 200007"的问题。

## 十六、前端 axios 封装契约

这是硬性要求，必须完全按此实现：

1. 创建单个 axios 实例，baseURL 取环境变量（值为 `/api`），超时 15 秒。
2. **请求拦截器**：
   - 从本地存储读 token（键名 `admin_token`），存在则加请求头 `authorization`，值为 `Bearer ` 加 tokenId。
   - 每次请求生成一个 traceId，加到请求头 `x-trace-id`。
   - 按当前语言设置请求头 `accept-language`（`zh-CN` 或 `en-US`）。
3. **响应拦截器**（**只依赖 code 与 data，绝不依赖 message**）：
   - 从响应头读取 `x-trace-id` 并记录，出错时打印到控制台，便于和后端日志对账。
   - code 等于 200：**直接把 data 字段返回给调用方**（调用方拿到的就是业务数据本身，不是整个包装体）。
   - code 不等于 200：按 `error.{code}` 取词条（取不到用通用未知错误文案）弹出提示，然后 reject 一个错误对象，对象上带 code 与 data（data 在校验失败时是校验错误对象，其余情况为 null）。**不要把 message 当作展示文案**，它只允许进 console 便于排查。
   - 特别处理 code 200003：清除本地 token 与用户状态，跳转登录页，并且要防止并发请求时重复弹窗、重复跳转（用一个模块级标志位加短时间窗口，或者只允许第一个 200003 走完整流程，其余静默 reject）。
   - 特别处理 code 100004：把 data（校验错误对象）透传给调用方，由表单定位到具体控件（见第 5 条）。不要在这一层弹出消息提示，避免"页面提示 + 表单红字"重复轰炸用户。
   - HTTP 层异常（网络错误、超时、非 200 状态码）：同样弹出提示并 reject，不要让它静默失败。
4. 对外导出的请求方法**只暴露 post**，业务代码不允许直接使用 axios 原始实例。方法要支持泛型，让调用方能声明返回数据类型。
5. 参数校验失败（code 100004）时，错误对象要带上 data（校验错误对象），便于表单按 field 定位到具体控件、按 reason 就地展示红字。**不要**在这一层再弹一次全局消息。
6. 业务代码里写的接口路径**不带 `/api`**（由 baseURL 提供）。
7. **并发与重复提交（必须实现）**：同一个接口 + 相同参数在途时，取消前一个请求（AbortController，按 method + url + 参数序列化生成 key）。搜索按钮、提交按钮点击期间置 loading；查询条件变化时对输入型条件做防抖（300ms 左右）。
8. **多标签页同步（必须实现）**：监听 `storage` 事件，其他标签页登出或 token 被清除时，本标签页同步清空 store 并跳登录页，避免"一个标签页登出、另一个还能操作"的错乱。
9. 本地存储键名、请求头名统一在一个常量文件里定义，禁止在页面里散落魔法字符串。

## 十七、Pinia 状态管理

| store | 职责 |
|---|---|
| user | token、用户信息、角色、超级管理员标志、权限集合；提供登录、登出、拉取当前用户信息、清空状态；权限集合要提供判断方法（超管直接返回 true，见 19.1） |
| permission | 后端菜单树、由菜单树生成并注册的动态路由、侧边栏菜单数据 |
| app | 当前主题、当前语言、侧边栏折叠状态、页面标题；这些状态要持久化到本地存储 |

store 使用组合式写法，全部带 TypeScript 类型。

**菜单树的两套用途要分清**：同一份后端菜单树，既要生成扁平化路由（18.3），又要渲染层级侧边栏。两者用途不同——侧边栏用原始树，路由用扁平化结果。不要把扁平化后的路由对象拿去渲染侧边栏，那样层级会丢。

## 十八、路由与守卫

### 18.1 静态路由

登录页、403、404、工作台为静态路由。布局路由为静态：path 为 `/`，name 为 `Root`，组件为布局组件，重定向到工作台页面；工作台（首页）作为它的静态子路由。

**工作台不进菜单表**：它是固定页面 `src/views/dashboard/index.vue`，侧边栏固定展示第一项，文案走 i18n。

### 18.2 组件定位规则（关键）

前端必须用 `import.meta.glob('/src/views/**/*.vue')` 建立一张全量组件映射表（key 为文件路径，value 为动态导入函数），**不要手写零散的 import 语句**。菜单对应的组件按以下优先级定位：

1. **菜单的 component 字段非空** → 用它的值查表，例如 `system/user/index` 对应 `/src/views/system/user/index.vue`。
2. **component 为空**（默认情况，日常配置都不用填） → 按路由 path 推导：path 为 `/system/user` 就找 `/src/views/system/user/index.vue`。
3. 两种方式都找不到 → 指向 404 页面，**不要抛异常导致白屏**。

这样日常新增页面零配置（只要目录结构与 path 一致）；万一某天菜单 path 与目录结构对不上，在菜单里填一次 component 即可解耦，改动不需要重新编译前端（只要目标组件文件已经在包里）。

**注意**：新增一个此前不存在的页面文件，仍然必须重新构建部署前端 —— 因为组件是编译期产物，glob 表在构建时就固定了，这一点任何方案都绕不过去。

### 18.3 动态路由

登录后（或在守卫里）调 `/admin/system/sysauth/me` 拿到菜单树，转换并注册。

转换规则：

1. 只处理 type 为 1 和 2 的节点，type=3 直接跳过（它们只贡献权限标识）。
2. **统一扁平化**：不做多层嵌套路由。所有生成的路由都通过 addRoute 挂到名为 `Root` 的路由下。目录节点本身不生成路由，只用于侧边栏分组。
3. 菜单节点的路由 path 去掉开头的斜杠（作为 Root 的相对子路径），这样最终 URL 就是菜单配置的完整路径。
4. 路由 name 用 `menu-{菜单id}`，保证唯一且稳定，供页面缓存 include 使用。
5. 组件按 18.2 的规则定位。
6. meta 里放：标题（菜单 name）、图标、keepAlive、visible（用于侧边栏过滤）、菜单 id。
7. visible 为 0 的节点：路由照常注册（可直接访问），但侧边栏不展示。
8. **刷新与重复登录都按服务端返回重建**：注册前先移除上一次注册的动态路由，避免重复 addRoute 造成的警告与缓存错乱。

侧边栏单独用菜单树渲染（Element Plus 的嵌套菜单组件），不复用扁平化后的路由对象，这样目录层级展示才不会因为扁平化而丢失。渲染前**补全祖先链**：若某菜单的父目录在数据里缺失，把它视为顶级节点渲染，不要因为找不到父节点而丢菜单。

**侧边栏展示规则**：目录下没有任何可展示子菜单时，该目录不渲染（避免出现空目录）；工作台固定在第一项。

### 18.4 守卫逻辑（必须按顺序）

1. 已有 token：
   - 目标是登录页 → 直接跳到首页。
   - 用户信息未加载 → 调 me 接口；成功后生成动态路由并用 `replace` 重新进入目标路由（保证动态路由已注册）；失败则清 token 并回登录页。
   - 用户信息已加载 → 放行。
2. 没有 token：
   - 目标在白名单（登录页、404、403）→ 放行。
   - 否则跳到登录页并带上重定向地址。
3. 每次导航设置文档标题为"页面标题 - 应用名"，页面标题取路由 meta 标题，缺失时用 i18n 默认值。
4. 使用 nprogress 显示顶部进度条。
5. 兜底：目标路由既不在静态路由也不在已注册的动态路由里 → 跳 404，**不要白屏**。

登出：调后端登出接口（失败也继续），清空 store 与本地存储，重置动态路由（移除已注册的动态路由），跳登录页。

## 十九、按钮权限指令与国际化

### 19.1 按钮权限指令

- 指令名 `has`，用法是传入权限标识字符串或字符串数组。
- **逻辑顺序（必须按此顺序写）**：
  1. 传入值为空（null / undefined / 空字符串 / 空数组）→ 不做任何处理，直接保留元素；
  2. **当前用户 `superAdmin` 为真 → 直接通过**（这是超管的唯一判据路径）；
  3. 否则判断用户权限集合是否包含任一传入标识；
  4. 不通过则**把元素从 DOM 中移除**（不是隐藏，避免被手动改样式绕过）。
- **不要**在指令里去匹配 `*:*:*` 字符串。超管之所以通过，是因为第 2 步的布尔判断。`*:*:*` 只是后端返回的可读展示值。
- 指令要能安全处理传入空值、绑定组件根元素、以及元素尚未挂载父节点的情况，避免报错。
- 页面中所有操作入口都必须用它包裹，**包括搜索按钮**（对应「查询」权限点）。
- 指令里用的权限标识必须与菜单表按钮行的 perms、后端接口地址三者完全一致。

同时通过权限 store 暴露一个判断函数，供少数需要条件渲染（而非移除）的场景使用；该函数同样按"空值处理 → 超管放行 → 权限集合匹配"的顺序实现，与指令共用同一套判断逻辑（抽到一个 composable 里，不要写两份）。

### 19.2 国际化

- 语言：简体中文（默认）与英文，键名结构对齐。
- 词条按模块拆文件后汇总：通用、登录页、布局与侧边栏、工作台、用户管理、角色管理、菜单管理、**字段标签（field）**、**校验消息（validation）**、错误码（error）。
- **错误码词条**：以数字码为键（对应第六章码表），保证后端返回任何码都有中文/英文提示。其中 `200004` 的文案要说清"该用户名曾被使用，不可复用"。这是前端翻译的**唯一来源**，不要参考返回体的 message。
- **字段标签词条**：键名为 `field.{字段名}`（例如 `field.username` = 用户名、`field.roleIds` = 角色）。这里的字段名必须与后端返回的 `data.field` 逐字一致——后端返回的是 DTO 字段名（`firstName` 这类就是驼峰），因此**前端表单项的 prop 也要用同样的字段名**，两边不要各写一套（不要给表单项起 `user-name` 这种别名，否则定位会失败）。
- **校验消息词条**：键名为 `validation.{reason}`，reason 只取 7.2 受控词表里的六个值（`required`、`len`、`pattern`、`email`、`range`、`type`），与后端校验注解上写的 message 逐字一致。
- **参数校验错误的文案拼装规则（前后端约定，必须照此实现）**：后端返回 `code=100004` + `data.field` + `data.reason` 时，前端按以下顺序取文案，取到即停：
  1. `validation.{field}.{reason}` —— 需要整句特例时用（例如 `validation.username.required` = 请输入用户名）；
  2. `field.{field}` 与 `validation.{reason}` 组合，英文用空格连接（例如 用户名 + 不能为空 / Username + is required）——**这是常规路径**；
  3. `error.100004` —— 字段名或 reason 没配词条时的兜底；
  4. 通用未知错误文案。
- 后端返回的 message 是调试短语，**前端不得用它做任何展示**；前端必须保证第 3 步一定存在词条（`error.100004` 是必填项）。
- 菜单名、角色名这类"数据"不走前端词条，直接显示后端返回值；界面上其余所有文案必须走词条，源码里不允许出现硬编码中文或英文句子。
- Element Plus 自带的组件文案（分页、日期选择、空表格等）也要跟随语言切换，通过其配置组件注入对应语言包。
- 语言切换要持久化到本地存储，并同步设置 axios 请求头。

## 二十、主题系统

三种主题：白（light）、黑（dark）、蓝（blue）。

### 20.1 实现方式

- 在根元素上同时维护两个标记：`data-theme` 属性（值为 light / dark / blue）和 `dark` 类名（仅黑主题时添加）。
- 用 CSS 变量定义主题：`data-theme` 选择器下分别声明一套变量。变量至少覆盖：主色、主色浅色变体（3/5/7/8/9 档，用于 Element Plus 悬停/禁用态）、主色深色变体、页面背景、卡片背景、侧边栏背景、侧边栏文字、侧边栏选中态背景、顶栏背景、正文文字、次要文字、边框色、分割线色。
- Element Plus 主题色通过覆写它的 CSS 变量（主色及其 light/dark 派生变量）实现；黑主题同时引入 Element Plus 官方的暗色变量样式文件。
- Tailwind 使用 class 策略的暗色模式（配合根元素 `dark` 类），业务样式优先用主题变量和 Tailwind 工具类，避免写死颜色值。
- 三套主题的具体观感：
  - **白**：页面浅灰背景、白色卡片、白色侧边栏、蓝色主色，默认主题。
  - **黑**：深灰近黑背景、深色卡片、深色侧边栏、蓝色主色，文字整体转浅。
  - **蓝**：深蓝侧边栏（商务感）、浅色内容区、白色卡片、蓝色主色，强调色更饱和。
- 全局风格要求：简洁商务风。圆角克制、阴影轻、边框细，字体大小与间距统一，表格与表单留白一致。不要在页面里出现花哨的渐变、动效、彩色卡片堆叠。
- 主题持久化到本地存储，刷新后保持；可额外提供"跟随系统"选项（非必需）。
- 切换主题时不允许出现闪烁（根元素标记要在应用挂载前尽早设置，可在入口文件读本地存储先设置一次）。

## 二十一、页面功能明细

### 21.1 登录页

- 居中卡片式布局，左侧或顶部有品牌区，输入用户名、密码。
- 校验用 VeeValidate + yup：用户名必填、长度限制；密码必填、长度 8-32。
- 支持"记住用户名"（写本地存储）、回车提交、提交时按钮 loading。
- 布局上提供语言切换与主题切换入口。
- 登录成功后：保存 tokenId、跳转到重定向地址或首页。
- 登录失败：按状态码弹出提示（密码错、账号禁用等），不暴露"用户是否存在"的细节。

### 21.2 工作台（首页）

简单商务风概览页即可：欢迎信息、当前用户与角色、几个统计卡片（用户数、角色数、菜单数）、系统信息（后端版本、前端版本、登录时间）。**不要引入图表库**，不要造假数据图表。

**统计数据必须走专用接口**：调 `/admin/system/sysauth/count`（只校验登录），返回 userCount、roleCount、menuCount。

原因：工作台是静态路由、所有登录用户都能进，但如果去复用带权限点的列表接口拿总数，普通用户没有查询权限时会拿到 200007、页面弹出错误提示或显示 0 —— 这是必然会被发现的体验缺陷。因此**不要**用列表接口凑统计。

系统信息里的前端版本用构建期注入的环境变量；后端版本不要为了显示去读磁盘或扫描依赖，如无接口则直接省略该行。

### 21.3 用户管理

- 查询区：用户名、昵称、状态、角色下拉；展开/收起；重置；**搜索按钮用「查询」权限标识包裹**。
- 表格列：用户名、昵称、邮箱、手机号、角色（标签展示，多角色并列）、状态（开关或标签）、创建时间、操作列。
- 操作：新增、编辑、删除（支持批量）、重置密码、启用/禁用、分配角色。
- 新增弹窗：用户名、密码、昵称、邮箱、手机号、状态、角色多选（必填，至少一个）、备注。
- 编辑弹窗：不含密码与角色，角色走独立的"分配角色"入口。用户名编辑时只读。
- 删除、重置密码、启停用都要二次确认（删除支持多选，走同一个批量入口）；删除当前登录用户、删除或禁用超级管理员要给出明确的后端错误提示。
- 新增时的用户名重名（200004）提示要说明"曾使用过的用户名不可复用"；密码强度规则（8-32、字母+数字）在前端也要提示。
- 所有操作按钮用按钮权限指令包裹。
- 创建时间用 dayjs 格式化（后端给的是毫秒时间戳数字）。
- 表格分页用公共表格组件，删除最后一页最后一条后自动回退页码；总条数是字符串，需转数字后交给分页组件。

### 21.4 角色管理

- 查询区：角色名、角色编码、状态；**搜索按钮用「查询」权限标识包裹**。
- 表格列：角色名、编码、排序、状态、备注、创建时间、操作列。
- 操作：新增、编辑、删除（支持批量）、分配菜单权限。
- 新增/编辑弹窗：角色名、编码、排序、状态、备注。
- 分配菜单权限：抽屉或弹窗内放菜单树（含目录、菜单、按钮三级，可勾选、可半选、支持展开/折叠、支持全选），保存时提交勾选的菜单 id 列表（建议同时提交半选父节点，保证父菜单可见）；**提交前对 menuIds 去重**。**每个角色单独配置权限**，默认不勾选任何权限。
- 超级管理员角色禁用编辑编码与删除操作，界面要有明确提示。
- 角色被禁用后，页面上要能看出该角色不再贡献权限（列表用状态标签体现即可，不需要额外提示文案）。

### 21.5 菜单管理

- 顶部工具区：新增根菜单、展开/折叠全部。
- 树形表格列：菜单名称（缩进体现层级）、图标、类型（目录/菜单/按钮标签）、路由路径、组件路径、权限标识、排序、显示状态、状态、操作列。**搜索按钮用「查询」权限标识包裹**。
- 操作：新增子级、编辑、删除。删除有子节点时必须提示不能删除。

## 二十二、日志与审计

### 22.1 logback 配置

放在 admin-log 模块的资源目录，文件名必须叫 `logback-spring.xml`。

- 通用：输出格式包含时间、级别、线程、**traceId**、类名、消息；不同级别用颜色区分（仅控制台）。
- **dev 环境**：只输出到控制台，级别 DEBUG（业务包）。
- **prod 环境**：异步输出到文件，按天与按大小滚动，保留 30 天，单文件上限 100MB，同时保留 ERROR 单独文件；控制台只输出 WARN 以上或关闭。
- 日志目录通过配置项指定，默认项目根下的 logs 目录。
- traceId 由 traceId 过滤器写入 MDC（见第九章），请求结束清理。
- 日志级别与 SQL 日志开关按环境区分（dev 打印 SQL、prod 关闭）。

### 22.2 请求日志切面

- 拦截所有 Controller 方法。
- 记录：请求地址、HTTP 方法、控制器方法、当前登录用户、耗时、返回码、traceId。
- 通过日志输出，**不写数据库**。
- 耗时超过阈值（默认 1 秒）时用 WARN 级别输出。
- 入参打印要脱敏：密码、token 字段必须替换为 `***`；长内容截断。

### 22.3 操作审计日志

- 自定义注解 `OperationLog`，属性：模块名、动作名（必填），可选的"是否记录入参"。
- 切面拦截带该注解的方法，成功与失败都记录（失败记录错误信息与返回码）。
- 写入 `sys_operation_log` 表，异步执行（用 Spring 的异步能力，配置独立线程池），写日志失败不能影响主流程。
- **异步上下文传递规则（必须遵守）**：切面在**同步阶段**就要把需要的数据全部取出——当前登录用户（从请求属性 `admin.loginUser`）、traceId（MDC 或请求属性）、耗时、返回码、截断后的入参——作为参数传给异步方法。**异步方法内部禁止**再读 ThreadLocal、请求属性、RequestContextHolder 或 MDC，那些在异步线程里是空的或错的。
- 线程池要有界：核心线程、最大线程、队列容量、拒绝策略都写清楚，拒绝时只打 WARN 日志，不抛异常影响主流程。
- 在用户、角色、菜单的增删改接口上标注该注解。分配权限、分配角色、启停这类"状态改变"接口也要标注。
- 切面获取当前登录用户时，只能从请求属性 `admin.loginUser` 读取（见 2.2 的循环依赖约束）。
- 审计记录里的 params 必须已脱敏（密码、token 一律 `***`）。

### 22.4 审计日志查询

本次不要求做审计日志的查询页面与接口（表建好、写入正常即可）。

### 27.4 验收执行方式（**执行验收的 AI 必须遵守**）

**本机环境限制：默认不要启动无头浏览器做校验**（Chrome / Chromium / Puppeteer / Playwright 的 headless 模式都会把这台机器卡死）。只有在走下面方式 A、并且用户明确同意之后，才允许短时执行浏览器验证；任何情况下都不要为了"顺手看一眼"而安装浏览器驱动或长时间挂着浏览器进程。

**1. 验证优先级**

能用命令行确认的，一律用命令行，不要开浏览器：

| 要验证的内容 | 用什么手段 |
|---|---|
| 响应体结构、状态码、鉴权结果、限流/权限拦截 | HTTP 请求（curl 或等价命令行工具），带上 token 头，直接看返回 JSON |
| 数据落库结果（逻辑删除、审计记录、关联表、密码哈希） | 直接查 MySQL |
| 缓存与过期行为（token、权限缓存、版本号） | Redis 命令行 |
| traceId 链路、异常堆栈、启动校验结果 | 读日志文件 |
| 路径命名规则、权限标识清单、路由表 | 读启动日志 + 直接调清单接口 |
| 前端类型正确性 | 命令行类型检查（`vue-tsc` 或等价命令），**不需要看界面** |
| 前端能否构建 | 命令行构建，检查构建产物存在与退出码 |

**2. 必须"看到界面"时的处理流程**

只有真实渲染效果或真实交互流程才能确认的项目（见 27.2 中标注 `【需人工确认】` 的条目），按以下顺序处理：

1. 先把待确认项一次性列清楚：要打开哪个地址、点什么、看什么、什么算通过。
2. **先问用户**：这一项是按下面的方式处理
   - **方式 A（AI 处理）**：AI 用浏览器截图或自动化方式自行验证。此方式仅限**用户明确同意之后**，且只能短时执行、验证完立即关闭进程。
   - **方式 B（人工确认）**：由用户自己在浏览器里看，看完给出结论。
3. 用户选择方式 B 时，等用户反馈：**反馈"通过"** 即该项通过；**反馈失败** 时请用户给出具体现象，AI 负责修，改完再请用户确认一次。
4. **30 秒内没有任何回应**，视为用户当前不在电脑前：此时 AI 不得擅自启动浏览器，改为用非浏览器手段尽可能验证（能查数据的查数据、能读代码的读代码），并把该项标记为**待用户确认**写进验收报告。
5. 全程不重复追问同一个问题；多个待确认项合并成一次询问。

**3. 服务与端口**

- 已经有人启动的服务就复用，不要反复重启。
- 需要启动服务时，启动前先确认端口可用；**不要擅自换端口**。
- 验证结束后保留服务运行状态，并把访问地址告诉用户。

**4. 报告要求**

验收报告必须把结论分成三类，不要混在一起：

1. **命令行已验证**（附命令与关键输出）。
2. **用户已确认**（附用户反馈）。
3. **待用户确认**（列明原因：需要视觉或交互）。

**不允许把"没能验证"的项目当作"通过"**。
